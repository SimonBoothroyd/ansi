# Tech debt tracker

Known, deliberate debt — what someone still owes. Add a row when you knowingly
cut a corner; delete the row when you fix it.

Three rules keep this a queue rather than an archive. A row whose Plan reads
"nothing to do", or whose Debt begins "Paid" / "Retired" / "Shipped", does not
belong here — a thing that was deleted is recorded in the plan that deleted it.
A row longer than one screen is a design doc wearing a table cell. An unbuilt
*feature* is not debt; it lives in [`backlog.md`](./backlog.md). There is no
date column: when a row was noticed is git's business, and what it costs is
this file's.

| app/test | **The write-guard invariant is held by a regex over source text.** `no_bare_repo_write_test.dart` derives the write set from the repository interfaces, then walks enclosing parentheses to decide whether a call sits inside `ref.write`. It is defeated by an aliased receiver nested inside something else, by a stored function reference (`final f = repo.deleteSection; f(id);`), and by a string literal containing parentheses. Thirteen allow-list entries carry deliberate exceptions with reasons. | A determined author, or an unusual call shape, slips a silent write past CI. | The same rule as a `custom_lint` in `packages/ansi_lints/` resolves the invoked element instead of matching text, and puts the squiggle in the editor. It would be the repo's first in-house pub package and must respect the load-bearing `custom_lint 0.8.x` / `riverpod_lint <3.1.0` pin — worth it only if the regex is actually evaded. |
| sync | **A dropped write is reported, not recovered.** The banner names the table, the operation and the server's code, and "I've seen this" retires the notice — it re-queues nothing, because the server refused the write and would refuse it again. Re-saving what the write changed is the only fix, and the user has to know what that was. | Someone taps through the banner believing it repaired something. | Only worth more if a drop is ever seen in the wild. The honest upgrade is naming the *row* rather than the table (`"Chicken Curry"`, not `recipe`), which needs a local lookup by id at report time. |
| sync/test | **Sync is untested against a genuinely failing or contended stack:** the offline-queue drain on network loss (airplane mode → reconnect), a true two-client concurrent-edit session (LWW and independent-row union, spec §3), and the escalation the banner exists for — five minutes of upload errors becoming a banner, and `Try now` reconnecting. The states, thresholds and copy are unit- and widget-tested over an overridden provider; `uploadData`'s put/patch/soft-delete mapping is unit-tested against a real `ps_crud`. | A wiring mistake between `statusStream` and the banner shows as an app that stays quiet in exactly the case the front was built for; a regression in reconnect or conflict handling slips entirely. | One errand: drive the sim with the local PowerSync container stopped, read the Shop line and the banner, then reconnect. A two-client session needs two sim clones against the local stack. |
| auth/dev | **Ghost users after `supabase db reset`, on the cached-household path only.** The onboarding path is handled — `ensure_onboarded`'s `23503` classifies as `accountMissing` and `/connecting` offers an honest Sign out. `_reconcile` (session.dart) hits the same ghost failure and deliberately swallows it, publishing `SessionReady` on the stale cached household, because flipping a live session into an error from a background reconcile would break the offline-first contract. | A dev signed in *before* the reset sees an empty-but-working app instead of the sign-out offer, until they sign out by hand. | The surface exists (`AnsiSyncBanner`, hosted once by the tab shell, advisory and never a state flip). What is left is the hook-up: an `accountMissing` case fed by `_reconcile`. |
| ingredients/search | **Tier 2 scans the whole live vocab in Dart, with no SQL `LIMIT`** — deliberately, because a cap would silently stop typo tolerance working for whatever fell off the end as a vocabulary grew, and the pass only runs when the SQL search already found nothing. Stated bound: correct to roughly **2,000 rows** on a phone. | Past a couple of thousand rows every missed keystroke reads the whole table and scores it in Dart, with no debounce in the picker either. The number is written down so a growing vocabulary degrades visibly instead of silently. | Add an index (SQLite FTS5 with the trigram tokenizer is the obvious one) when a household's vocabulary approaches the bound — not before. Contract: [`search-and-matching.md`](../design-docs/search-and-matching.md). |
| ingredients/device | **Everything with a lens is one physical-device errand, and Android's back rides with it.** `mobile_scanner` compiles its still-image `analyzeImage` out on the iOS Simulator, and a camera-less sim never *errors* — it waits — so nothing has run: ① **scan-from-photo** (build it *and* verify it); ② photo-import **camera capture** (built: "Take a photo" beside "Choose photos" on the intake form — but the shot, its crop and the camera-denied error have only run against the injected seam); ③ a **live scan** off a real pack; ④ the **camera-denied** notice rendering; ⑤ the density-row overflow and the stranded-default flag on a real screen. Android's predictive back (`enableOnBackInvokedCallback` + the shell's `PopScope`) is covered only against the platform channel: nothing proves `canPop: false` still starts the system animation, or that a back at the Library tab previews the launcher. | The one entry point designed around hardware is verified through its typed sibling only, and the one platform whose back button is a first-class control is verified in a simulated binding only. | One sitting on a real phone in that order — ② and ③ share the camera plumbing, ④ falls out of ③ by refusing the prompt, ⑤ is two screenshots — then one API 34+ emulator session: drag back from Shop, drag again, pop a pushed recipe. |
| books/ui | **Reorder is up/down menu items, not drag-and-drop, at both levels.** Books have the idiom sections already had, and there is exactly one path to it: `Move up` / `Move down` on the book's own `⋯`. | Clunky for many sections, and for many books. | A reorderable list when Forui offers a drag handle, or Material's `ReorderableListView` wrapped — books and sections convert together, on the row, never in a sheet. |
| books | **The Library's widget tests use fakes, not the real-DB harness.** They drive every Library mutation that crosses a dialog (rename, both delete refusals and the empty-book confirm, move contents, reorder, fold), which is what closed the original `ref`-after-dialog crash; the recipe and section mutation flows elsewhere are still covered only by the simulator smoke. | A provider-lifecycle bug on a still-uncovered path reaches the phone. | Point the Library tests at the real-DB harness if a fake ever hides something, and extend the same treatment to the recipe editor's dialogs. Standing rule meanwhile: mutations go through keep-alive repo providers. |
| app/test | Host repo tests need an extension-capable SQLite; macOS's system build omits extension loading, so `test_db.dart` falls back to Homebrew's `libsqlite3.dylib`. The Linux/CI half is paid — the `app` workflow installs `libsqlite3-dev` and runs the real-`PowerSyncDatabase` suite on `ubuntu-latest`. | A machine without `brew install sqlite` cannot run `make test-app` locally. | Nothing scheduled — CI proves the Linux path continuously. Revisit if the sqlite3 package ever ships a bundled host library. |
| app/ui | **Four framework assertions are filtered in the sim smoke** (`integration_test/support/drive.dart`): any exception whose text names `semantics.dart` (a Forui dialog opened with the semantics tree live), a deactivated ancestor under `_updateSelectionRects`, the same under `EditableTextState.didChangeMetrics`, and any stack through `_scheduleShowCaretOnScreen` — a popped form's still-focused field firing a frame late against a defunct element. Three are narrowed by stack; the semantics one matches on the message alone. The caret one matters beyond the noise: that callback **scrolls the enclosing viewport**, which is why the ingredients file's post-return assertions scroll rather than wait. | Each filter could mask a real regression in its own family, and the list has grown from two to four without anyone deciding it should. A user-visible symptom is plausible on the same mechanism though unobserved: pop a form with the keyboard up and the list behind it can come back oddly scrolled. | Re-check all four on every Flutter/forui upgrade and delete the ones that stop reproducing; narrow the semantics filter to a stack. If the scroll jump is ever seen for real, the fix is unfocusing before the pop, not a wider filter. |
| app/ui | **Three await-a-sheet sites are held by the structural test alone** — the editor add-line, the shopping top-up and the week add-flow. Every site captures `hostContextOf` before the await; the top-up also captures `ProviderScope.containerOf` and writes through `container.write`, while the add-line hands the write to the editor notifier and the add-flow to the confirm sheet. `no_ref_after_await_test.dart` holds the rule tree-wide, but a widget test cannot unmount one card of a lazy list without unmounting the screen: a host test drives the top-up as far as its quantity sheet, and the other two run only on the simulator. | A regression at one of those three sites would pass every host test and drop a confirmed action on a phone, silently, exactly when the keyboard has pushed the row off screen. | Nothing scheduled unless a lazy-list unmount harness becomes cheap; the structural test is the guard. |
| cook_plan | **A persisted per-session override store is unbuilt, and four things want it:** the **cook day** (always the earliest covered day — the timeline handle is not draggable), the **per-week** cook day the week rows now print off `buildCookPlan`, the **whole-batch nudge** choice (it advises cooking ×1 while the list keeps buying the honest ×0.75, and says so), and the nudge **toggle** itself (an autoDispose provider per session, so it resets when the tile scrolls out or the app restarts). | A cook who follows the nudge under-buys and tops up by eye; the toggle resets under the thumb. | One store, read by all four. Stretch — build it when the resets annoy in practice. |
| cook_plan/ui | The freshness timeline (`_TrackPainter`) draws on the week's own seven-day axis with a 7-day ruler. `CookTimelineSpec` is unit-tested (day coords + tails) and the painted bar is sim-verified, but it is not golden-tested, and multiple meals on one day collapse to a single marker. | A rendering regression could slip; a two-meals-one-day session under-marks. | Add a golden test if the bar changes often; badge multi-meal days if it matters. |
| pickers/ui | The ingredient picker's "Recent" section derives from live usage (recipe lines + manual top-ups), not a selection history — picking something and then deleting its line drops it from Recent, and a fresh household shows the alphabetical list instead. | Recents are less sticky than a true history. | Add a local selection-history store only if the derived feed annoys in practice. |
| recipes | The `Recipe` aggregate does not carry `favorite`; the recipe page resolves the flag from the list-summary stream instead — an extra watch, and by design `saveRecipe` cannot clobber the flag. | Mild indirection; a second subscription on the recipe page. | Fold `favorite` into the aggregate if the page grows more list-summary needs. |
| recipes | **A step's stable key is derived from its prose, so identical steps collide.** `MethodStep` has no `id` — the `steps` jsonb is the frozen §4.6 contract and a new key would land in every row the import commit writes — so `stableStepKey` hashes the step's own text. It survives a reorder; two byte-identical steps do not tell apart. | Nothing today. When cook mode lands, a recipe with two identical step sentences could resume on the wrong one. | Decide it with cook mode, the only consumer: accept the collision, or add the id in the same change that touches §4.6 for the step token carrying a `recipe_id` — one contract change, not two. |
| recipes/ui | **`no amount` and `ingredient removed` are the two markers on the recipe page that route to the EDITOR.** Every other named line is a door to the thing that fixes it — the ingredient's form for a missing density or piece weight, the sub-recipe for its own gaps — but these two push `/recipes/:id/edit`, because the page has no writer for a line's amount and its line picker lives in the editor. | Two reasons of ten are two taps and a screen change. | Give the recipe page the shipped quantity sheet and the line picker for a single line, or accept the editor hop and say so on the marker. Wants a ruling on whether a read-only page should write at all. |
| recipes/ui | Two Forui 0.22.3 workarounds: a custom underline tab bar (`_TabBar`) and a custom hairline (`_Hairline`, because `FDivider` bakes in a 16 px margin). The tab bar's original blocker is gone — `FVariants` is exported now and the theme already uses it — so an underline `FTabsStyle` may be reachable; nobody has tried. | Diverges from Forui; extra code to maintain. | On the next touch of the recipe page's tabs, try the styled `FTabs`; delete `_TabBar` if it holds. Revisit the hairline if Forui gains a zero-margin divider. |
| import/matching | **A `none` line throws away the candidate the cascade already ranked first.** §6 says `none` (< 0.55) carries empty candidates, so a line the engine scored just under the floor reaches the review with an empty picker and "Find or create ingredient" — no help at all where the engine had the answer in hand. The two lines that first showed it (`extra virgin olive oil`, `cooked Puy or green lentils`) now resolve, because the vocabulary gained the rows; the band rule is unchanged, and `sample_payloads.dart`'s doc comment still explains its `none` lines with the old vocabulary. | The screen looks like it knows nothing about a line it nearly knew, which is exactly when a cook stops trusting the import — and the one-tap correction that would teach the alias never happens, so it stays wrong next time. | Decide it as a band question, not a patch: either `none` keeps its top-N as offers under a weaker heading (a client + `types.ts` + golden-fixture change, and the eval re-calibrated), or the floor moves. Re-measure vectors against the current snapshot first, and fix the canned payload's comment in the same slice. |
| import | **The nested-recipes import leg is host-tested only, never sim-driven.** The "↪ your recipe" offer chip, the linked-line save gate and the Review MAKES row ship, but the canned sim payload carries no `recipe_candidates` (there is no stable local recipe id to point one at) and the real matcher lives behind the edge function. | A regression in the review-side linking (chip render, unlink, Save arithmetic, `yield_raw` prefill) would pass `make test-sim` and surface only on a live import. | Either teach the canned-payload path a late-bound candidate (inject a seeded recipe id at run time), or fold a live edge-fn import into the next device/cloud errand. | test-sim | **The import file's method-edit leg is unwritten:** type into step 2 at review and assert the saved `refs`. | test-sim | **A run whose app "goes quiet" is diagnosed by looking at the simulator, and nothing says so.** A modal *system* alert left on the device by an earlier session — a camera or photo-permission prompt, say — keeps scene focus, so the freshly installed app launches behind it, never becomes active, and the integration-test binding never starts: no Dart error, no test line, the app idle at 0 % CPU until the run is killed. Dismissing the alert costs one tap. | The symptom is indistinguishable from a hung `setUpAll`, and the run prints nothing to say otherwise — an hour goes into `_provisionHousehold` and the VM-service attach before anyone screenshots the device. | Make the failure *speak*: a bounded wait around the binding's first frame that fails with "the app never became active — is a system alert on the simulator?". Meanwhile: screenshot the sim first, and clear stale alerts before a run. |
| test-sim | **One watch-timing flake left:** `recipe_repository_test`'s "watchRecipe re-fires when a measure is renamed", seen twice under load — during a `make ci` that overlapped an iOS build, and again while seven parallel lanes shared one machine. | A rare red erodes trust in the suite if it recurs unexplained. | Pin the emission (await the specific watch tick) rather than pad a timeout. Do not run `make ci` and a sim build concurrently when a red matters — and check for orphaned `flutter_tester` processes first: three were found running for four and five days, and the host's load average reached 117. |
| ingredients/normalize | **"crushed" is held out of the normalizer's `CANNED_CUT_WORDS`.** The cut-word carve-out admits chopped + diced only, because `Canned Crushed Tomatoes` holds the generic `tomato canned` key the seeded `can` measures hang off; a `1 can crushed tomatoes` line therefore keys differently from a diced or chopped one. | The cut-word rule reads as arbitrary until crushed joins it, and a crushed line lands on the generic row rather than its own. | Rename Canned Crushed Tomatoes in the app so it stops holding the generic key, re-export the snapshot, then add `"crushed"` to both normalizer mirrors in the same slice; the reseed retires the old key on its own. |
| seed/usda | **`seed_usda.sql` is not re-runnable** — 8,204 plain inserts into a primary-keyed table, so the deploy button's reseed skips it once `usda_food` is populated. Re-run `seed_usda_index.sql` after any change to `usda_food`. |
| ingredients/normalize | **The `(ch\|sh\|x\|z\|s)es$` rule mangles genuine plurals whose singular ends in `-se`** — `cheeses` → `chees`, `pulses` → `puls`, `mousses` → `mouss`. Related, same shape: `cookies` → `cooky` via the `-ies` rule (103 `usda_food` rows). Both mirrors are bug-compatible and no vocab row hits it today. | A stored key that is a non-word is harmless while both sides agree; it becomes a stranded row the day one side is fixed alone. | Fix on BOTH sides in one slice with a whole-word `match_text` rewrite migration (template pre-checks raise on a unique-index collision). The invariant-word set is not the tool — this needs an `-ses` → `-se` rule with its own exception list (`glasses` and `classes` are right under the current rule and must stay so; `molasses` is the one invariant word today). |
| deps | **The Android build still runs the legacy Kotlin Gradle Plugin path.** `mobile_scanner` 7.4.0 already supports built-in Kotlin; what keeps the legacy path is the app's own `android.builtInKotlin=false` in `app/android/gradle.properties`, against AGP 9.1 and KGP 2.4. Flutter is pinned exactly (3.47.1), so it cannot surprise us. | A future Flutter bump fails the Android build until the flag is flipped. | Flip the flag and run a release Android build (CI's `release` workflow rehearses it without a tag); keep it off only if a plugin refuses. |
| scaffold | Version floors in `app/pubspec.yaml` are caret ranges (one deliberate bounded range, `riverpod_lint`). `pubspec.lock` **is** committed, so resolution is pinned in practice. | Loosened floors could drift on a `pub upgrade`. | Tighten floors when a resolve conflict actually shows; the lock carries it until then. |
| app/comments | **Decision letters (`D3`, `E7`, `U-D2` …) survive in about 380 `lib/` comment lines across 92 files.** The transcript-comment guard deliberately does not match them: `D3`/`E5` occur as hex-colour fragments and real identifiers, so a regex would cry wolf. | A reader needs the (archived) plan open to decode a ruling; the rule the comment states is usually still legible without the letter. | A hand pass, file by file, striking the letter and keeping the rule; then lower the count in a ratchet test. |
| recipes/ui | **The component line's amount keeps its own control.** Every other place a number meets a unit goes through the one `AmountAndUnitField` — density both ways, piece weight, measures, serving, yield — but `component_quantity_sheet.dart` still builds its own, because a component counts in `batch` ∪ the yields' families, no density exists for a recipe, and the chip row is what shows an off-filter pick. | Two amount controls to keep in step. A number rule fixed in `AmountAndUnitField` — fraction parsing, the off-filter marking — has to be remembered here separately, and a divergence reads as a component line that behaves unlike every other line. | Either lift the component's chip source into `AmountAndUnitField` as an injected filter, or rule that the component sheet is deliberately its own control and pin the two to the same number behaviour with a shared test. Decide it the next time either file's number handling is touched. |
| ingredients | **The row's serving round-trips through its own label text.** It is stored as an `ingredient_measure` labelled `serving · 1 cup`, and `serving_measure.dart` both writes that phrase and parses it back. The round trip is deliberate — a household can rename or bin the serving in the measures editor, and a label that stops parsing stops being read as a serving rather than becoming a second source of truth — but writer and reader must agree on the number format forever. | They have drifted once already: printing amounts as fractions made `1 1/2 fl oz` unreadable and the row silently lost its serving. The failure is quiet by design, so the next drift is found by someone noticing an absence. | Both halves go through the shared number reader now, and `serving_measure_test.dart` pins the round trip. The durable fix is to store the serving's amount and unit beside the label, which is a migration and a §4.6-shaped contract change — worth it only if the phrase drifts a second time. |
