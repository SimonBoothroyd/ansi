# Exec plan: 0031 — Week v3 — the mode goes, and each tap gets its own drawn target

- **Status:** done — retrospective, written 2026-09-04 from the design board's
  prose before it was cut. The work itself landed 2026-09-03.
- **Owner:** Simon (rulings) + Claude (design lane, then build)
- **Roadmap step:** 8.13 (follow-up to the Week v2 polish pass, plan 0022)
- **Created:** 2026-09-03

## Goal

Week v2 bought a resting screen by putting a mode on it — `Edit` / `Done` — and
justified the mode on one claim: *the mode changes what a tap means*. v3 asks
whether the mode was ever the cheap way to pay for that, decides it was not,
and deletes it — without losing a single thing the mode's screen could do.

The owner opened it:

> "I don't think edit and a separate page earns its keep any more"

> "can't we just have tap opens recipe, a minus sign clears it?"

## What shipped

Commits `386393e` (the mode goes, each tap gets its own target), `c63728a`
(`setDaySlot` goes with the entry sheet), `3a41e1d` (the format pass the
landing left behind) and `44c3377` (the sim smoke driving v3's targets), plus
`a16e408` (the docs catching up) and `d6f42dd` (the lane merge).

- One state. `WeekMode`, `_ModeAction` and the mode threaded through
  `_DayCard → _SlotGroup → _DishRow` are gone; so is
  `enterWeekEditMode` in `integration_test/support/week.dart`.
- `entry_sheet.dart` (328 lines, one caller) is deleted, and
  `PlanningRepository.setDaySlot` with it — interface, implementation, its
  test and four doubles.
- The row's three targets: the title opens the recipe, the portions chip +
  eater avatars are **one** target opening `meal_editor_sheet`, and a muted
  `−` removes the meal behind an undo toast.
- One `AddMealLine` per day card — its last row, above the day's total,
  reading `add a meal` or `nothing planned`.
- Cook markers and the day macro line are never hidden.

## Decision log

Recorded here from the board's "Week · v3" locknote and its three frames.
The rulings are the board's own numbering.

- 2026-09-03 — **The trigger.** Owner: *"I don't think edit and a separate
  page earns its keep any more."* Three things had eaten v2 D1/D7's claim
  that the mode changes what a tap means. (i) D5b gave presentation its own
  add doors, so edit's exclusive door was down to "a day that already has a
  meal" — the one add path in the app hidden behind a mode. (ii) Edit blanked
  the numbers you were editing against: it forced the cook marker to null and
  replaced the day macro line with the add door, so the mode that mutated the
  week was the mode that hid the consequence. (iii) Neither tap was
  destructive, and a mode earns its keep when the wrong tap is *dangerous*,
  not when it is merely different. Underneath, `showEntrySheet` had exactly
  one caller, and so did `setDaySlot`, `setEaters` and `setPortions`. The
  question in one line: **are three writes worth a screen?**

- **E1 — the mode goes.** One state, no `Edit` / `Done`, `WeekMode` deleted.

- **E2 — a dish row opens the recipe, always.** The `›` leaves with the mode
  that needed it: it announces that the row navigates and so competes with
  the row itself.

- **E3 — a quiet `−` at the row's right removes the meal, and an undo toast
  — not a confirm — is what makes it safe.** Owner-ruled the same day.
  Refused: a confirm dialog (it taxes every removal to prevent a rare
  mis-tap); a red `−` (the colour was never the safety, and this is a screen
  whose whole job is calm reading); swipe-to-delete as the only path
  (undiscoverable, and v3's whole argument is against invisible doors). The
  toast's second line names what would come back — `dinner · Ada & Jun · 1¾
  portions` — because an undo you cannot audit is a promise, not a control.

- **E3a — undo, not a confirm, and a deliberate once-only rule break.**
  Owner: *"undo toast"*. The argument: *a destructive control on every row of
  a resting screen is defensible only if the act is trivially reversible* —
  so v3 **makes** it so rather than asserting it already is (recipe · day ·
  slot · eaters · portions are all in hand). Carrying the undo means using
  the errors lane's toast surface for something that is not a failure, which
  breaks that lane's **"no success toasts"** rule. It is broken here once,
  deliberately, and the reason is narrow: this toast is not reporting
  success, it is *carrying the undo*, which is the only reason it exists.

- **E4 — the entry sheet is deleted, as a hub.** Nothing is reached any more
  by tapping a meal "to see everything about it". `setDaySlot` goes with it
  entirely: a repository method no screen can call is dead code with a
  passing test, which asserts a contract nothing holds. Day · slot is changed
  by remove-and-re-add through the recipe picker's already-this-week quick
  picks — which stop being a convenience and become load-bearing.

- **E5 — one add door in every state.** `＋ add a meal` as the last row of
  every day card; on an empty day the same widget reads `nothing planned`. It
  sits with the meals, above the total: it adds a meal, not a number.
  Rejected: keeping the dashed `＋ Add a meal` box always on — seven permanent
  dashed rectangles are the noise v2 built the mode to escape.

- **E6 — the cook markers and the day macro line are never hidden**, because
  there is no longer a state that could hide them.

- **E7 — a row's controls are the facts the row prints.** Owner: *"shouldn't
  tapping the portions or user icon open an editor?"* The title opens the
  recipe it names; the portions chip + avatar stack are **one** target
  opening a compact editor holding exactly those two fields
  (`MealEaterPicker` + `MealPortionsStepper`, straight out of
  `meal_fields.dart`, so the add path and the edit path still cannot drift).
  One target and not two, because the chip is conditional — it is drawn only
  when the override differs from the eaters' demand — so a chip-only tap
  would be missing from most rows and could never *set* a first override.
  The chip and avatars share one ~44 pt region at the row's right, so the
  target exists identically on every row.
  - **The line that keeps E4 from being a regression, and it is stated
    nowhere else:** *a field editor is reached by tapping the values it
    edits; a hub is reached by tapping the thing.* The entry sheet was
    reached by tapping the meal and answered "everything about this meal" —
    which is why it needed a mode to hide it. The E7 editor is reached by
    tapping the values it edits and holds nothing else: no second route to
    the recipe, no remove.
  - Rejected inside E7: the chip alone as the target (drawn only when an
    override exists); an always-on portions chip to fix that (it would print
    `1¾` on every row to serve the rare case, and the avatars already say
    who); day · slot in the editor too (the row does not print a day as a
    value — its position is its day — and putting it back is how the hub
    grows again).

- **What v3 refuses.** No confirm dialog on remove. No door with no surface —
  no long-press, and no swipe-to-delete as the only removal. The test is not
  "how many targets does the row have", it is **"is the target drawn"**: a
  long-press has nothing on screen to aim at, whereas the avatars and the
  portions chip are printed values, and tapping a printed value to change it
  is the plainest thing a touch UI does. No return of the per-row `⋯` (v2
  retired it) and no edit mode under another name — not a segmented
  `[Read|Edit]`, not a second route.

- **E4a, asked and answered.** Whether losing the two-tap eaters edit was
  acceptable: E7 answered it by giving the edit to the values themselves, so
  the deletion stands and the edit gets *cheaper*.

## Notes

- **What the sim run found** (`44c3377`, `make test-sim FILE=week` → 1/1,
  45 s, iPhone 17 against the local stack). The widget tests were green and
  `dart analyze` clean; running it for real found two things neither can see.
  1. **The undo toast eats the next tap.** It sits bottom-centre for six
     seconds — exactly where the confirm sheet's controls are — so a tap on
     the portions stepper's `+` landed on the toast. `pumpUntilGone` joined
     `pumpUntilFound` in `support/drive.dart` (the toast is the first thing
     in the app that leaves on a *timer* rather than on a write), and the
     removal leg now waits it out, which also asserts that it goes.
  2. **A 0027 leg still opened the editor by tapping the dish**, which under
     v3 opens the recipe. It taps the `EaterAvatarStack` now.
- Blast radius as built: 3 lib files, 4 widget tests,
  `integration_test/support/week.dart`, the spec's Week screen section and
  `features/planning/README.md`.
- `meal_fields.dart` keeps both its consumers and therefore its whole reason
  to exist: the confirm sheet and E7's editor are the same two controls.
