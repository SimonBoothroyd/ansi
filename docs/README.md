# The Ansi knowledge base

This `docs/` tree is the **system of record**. The guiding idea (from OpenAI's
[harness engineering](https://openai.com/index/harness-engineering/)): a coding
agent can only reason over what's *in the repo*. Knowledge in a chat thread, a
Google Doc, or someone's head is invisible to it — and to a human contributor
three months from now. So we write it down here, version it with the code, and
keep it in sync mechanically.

## How it's organised (progressive disclosure)

`AGENTS.md` at the root is a **map** — a short table of contents. It points here.
You start small and stable, then follow links to depth only where a task needs
it. Nothing tries to cram the whole system into one file (that approach rots).

```
AGENTS.md                    map / entry point (~100 lines)
ARCHITECTURE.md              top-level map of domains + layering
docs/
├── README.md                ← you are here: how the harness works
├── design-docs/
│   ├── index.md             catalogue of design knowledge
│   ├── core-beliefs.md      agent-first operating principles ("golden rules")
│   └── *.md                 mechanics explainers for OUR system, traced to code
├── decisions/               ADRs — immutable records of *why*
├── product-specs/
│   ├── index.md             catalogue of product behaviour
│   ├── product-spec.md      the full app spec
│   ├── import-and-matching.md   import/matching design
│   └── board/               the visual design board — one file per screen
├── exec-plans/              plans as first-class, checked-in artifacts
│   ├── roadmap.md           what is next, and what shipped
│   ├── active/              one file per in-flight non-trivial task
│   ├── completed/           finished plans, kept for history
│   ├── _template.md         copy this to start a plan
│   ├── backlog.md           unbuilt product ideas (not debt)
│   └── tech-debt-tracker.md known debt, paid down continuously
├── generated/               DO NOT hand-edit — regenerated by `make docs`
│   ├── db-schema.md         the schema, parsed from supabase/migrations/
│   └── unit-admission.md    the unit table, run from the Dart admission rule
├── references/              offline knowledge of key dependencies (llms.txt)
├── cloud-setup.md           standing up real cloud infra (Supabase/PowerSync/Google)
├── release.md               shipping to it: release tags + Supabase deploys
└── SECURITY.md              secrets, auth, RLS
```

## The rules that keep it honest

1. **A doc describes the system as it is now, in the present tense.** History
   lives in exactly three places: an ADR (why a decision was made), a plan in
   `completed/` (how a piece of work went), and git (everything else). A
   current-state doc may carry a date only when the date is a *fact about the
   system* — a version pin, a dependency release, a licence term, a scheduled
   cron — and never a landing date, a sign-off, an owner quotation, a commit
   hash, a test count, a wall-clock timing or a plan/lane/decision code. When
   you want to record that something changed, ask whether a reader who never
   saw the old version needs the sentence: if not, it is a commit message; if
   so, write the new behaviour, not the change. **The obituary rule:** a thing
   that was deleted is recorded in the plan that deleted it — the tracker holds
   only what someone still owes. Two carve-outs, deliberately append-only
   because the dates *are* the record: [`cloud-setup.md`](./cloud-setup.md)'s
   ledger and [`release.md`](./release.md)'s tag list.
2. **Docs change with code.** If a PR changes behaviour, it updates the relevant
   doc in the same PR. A stale doc is a bug, not a nicety.
3. **Decisions are immutable.** An ADR is never edited to say something new; a
   reversal is a new ADR that supersedes the old one.
4. **Plans are checked in.** Non-trivial work gets an exec plan in `active/` with
   its intent and a decision log, moved to `completed/` when done. Trivial changes
   don't need one. A finished record is never rewritten to match a later name,
   so plans and ADRs written before the **Mise → Ansi** rename still say "Mise"
   inside; anything describing the app today says Ansi.
5. **Generated docs are generated.** Anything in `generated/` is produced by
   `scripts/gen_docs.sh` (`make docs`) from a source of truth — `db-schema.md`
   is parsed from `supabase/migrations/`, `unit-admission.md` is run from the
   Dart admission rule in `app/`. Never edit by hand;
   rerun `make docs` (idempotent) after changing a migration and commit the
   result. `make docs-check` regenerates it to a temp file and diffs, so a
   skipped `make docs` fails CI rather than rotting.
6. **It's enforced mechanically.** `make docs-check` (CI job `docs`) is the
   hobby-scale stand-in for OpenAI's "doc-gardening" agent — see below.

## Doc-gardening (how this scales later)

At OpenAI scale, a recurring agent scans for docs that no longer match code and
opens fix-up PRs. We don't need that yet. The v1 equivalent is
`scripts/check_docs.sh`, run by `make docs-check` and by CI. Each check catches
one class of drift that has actually happened here:

- **Required files exist**, and **every relative markdown link resolves**.
- **Sync-rule boundary** — the local and cloud stream YAMLs have not diverged.
- **The generated docs are fresh** — `gen_docs.sh` is re-run to temp files and
  diffed against both files in `docs/generated/`, so a migration or an
  admission-rule change that landed without `make docs` fails here rather
  than in a reader's face.
- **No plan in `active/` says "done"** on its Status line, and a plan whose
  newest date stamp is over a week old **warns** — a finished plan that never
  moved to `completed/` is how the roadmap goes quietly wrong.
- **Table integrity** in the tracker and `ARCHITECTURE.md`'s standing table (a
  stray blank line silently splits one table into several, and the later ones
  render headerless), and **no duplicate area** in the standing table.
- **Every ADR in `decisions/` is linked from `design-docs/index.md`.**
- **A date budget** — more than one date per twenty lines in a current-state
  doc warns. This is the one check that measures the disease rather than a
  symptom; the append-only records are excluded.

The roadmap's **Next** list is the freshness signal for build progress. When you
(or an agent) notice a doc drifting from reality, fix it immediately — and if it
is a repeating class of drift, add a check here.

The point is the same at every scale: **capture human taste once, enforce it
continuously.**
