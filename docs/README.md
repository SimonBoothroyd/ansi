# The Mise knowledge base

This `docs/` tree is the **system of record**. The guiding idea (from OpenAI's
[harness engineering](https://openai.com/index/harness-engineering/)): a coding
agent can only reason over what's *in the repo*. Knowledge in a chat thread, a
Google Doc, or someone's head is invisible to it — and to a human contributor
three months from now. So we write it down here, version it with the code, and
keep it in sync mechanically.

## How it's organised (progressive disclosure)

`AGENTS.md` at the root is a **map** — a short table of contents. It points here.
You start small and stable, then follow links to depth only where a task needs
it. Nothing tries to cram the whole system into one file (that approach rots).

```
AGENTS.md                    map / entry point (~100 lines)
ARCHITECTURE.md              top-level map of domains + layering
docs/
├── README.md                ← you are here: how the harness works
├── design-docs/
│   ├── index.md             catalogue of design knowledge
│   ├── core-beliefs.md      agent-first operating principles ("golden rules")
│   └── *.md                 mechanics explainers for OUR system, traced to code
├── decisions/               ADRs — immutable records of *why*
├── product-specs/
│   ├── index.md             catalogue of product behaviour
│   ├── product-spec.md      the full app spec
│   ├── import-and-matching.md   import/matching design
│   └── design-board.html    the visual design board
├── exec-plans/              plans as first-class, checked-in artifacts
│   ├── roadmap.md           the ordered build sequence + live status
│   ├── active/              one file per in-flight non-trivial task
│   ├── completed/           finished plans, kept for history
│   ├── _template.md         copy this to start a plan
│   └── tech-debt-tracker.md known debt, paid down continuously
├── generated/               DO NOT hand-edit — regenerated by `make docs`
│   └── db-schema.md
├── references/              offline knowledge of key dependencies (llms.txt)
├── cloud-setup.md           standing up real cloud infra (Supabase/PowerSync/Google)
├── QUALITY.md               the quality bar + per-area grades
└── SECURITY.md              secrets, auth, RLS
```

## The rules that keep it honest

1. **Docs change with code.** If a PR changes behaviour, it updates the relevant
   doc in the same PR. A stale doc is a bug, not a nicety.
2. **Decisions are immutable.** An ADR is never edited to say something new; a
   reversal is a new ADR that supersedes the old one.
3. **Plans are checked in.** Non-trivial work gets an exec plan in `active/` with
   its intent and a decision log, moved to `completed/` when done. Trivial changes
   don't need one.
4. **Generated docs are generated.** Anything in `generated/` is produced by
   `scripts/gen_docs.sh` (`make docs`) from a source of truth — today that is
   `db-schema.md`, parsed from `supabase/migrations/`. Never edit by hand;
   rerun `make docs` (idempotent) after changing a migration and commit the
   result.
5. **It's enforced mechanically.** `make docs-check` (CI job `docs`) validates
   that internal links resolve and the required files exist. This is the
   hobby-scale stand-in for OpenAI's "doc-gardening" agent — see below.

## Doc-gardening (how this scales later)

At OpenAI scale, a recurring agent scans for docs that no longer match code and
opens fix-up PRs. We don't need that yet. The v1 equivalent is:

- `make docs-check` — link/structure integrity, runs in CI.
- The roadmap's Status column is the freshness signal for build progress.
- When you (or an agent) notice a doc drifting from reality, fix it immediately
  and, if it's a repeating class of drift, add a check to `scripts/check_docs.sh`.

The point is the same at every scale: **capture human taste once, enforce it
continuously.**
